Building the Box Score

01Why a league needs a stats site

BWB Wiffleball started in 2012 as six teams and seven players in my backyard. Fifteen years later it's six teams, dozens of players, a full regular season and postseason every year, and — as of this year — our first appearance at the NWLA national tournament. Somewhere in there, the league outgrew what a spreadsheet and a blog could hold.

We had every box score going back to 2017 sitting in a big JSON file: batting lines, pitching lines, fielding, game-by-game, year-by-year. What we didn't have was a way to actually see any of it — no career leaderboards, no park factors, no way to look up a player's career OPS+ without doing the math yourself. So I set out to build the site that data deserved, using Claude to do the actual engineering while I directed what it should look like, what it should say, and whether a given feature was actually good.

02Two files, one static site

The whole site comes from exactly two files. players.json holds every player, team, game, and award the league has ever recorded. generate.py is a Python script that reads that file and writes out a single self-contained index.html — one page, client-side routed, no backend, no database, nothing to keep running. GitHub Pages just serves the file.

That shape made the whole project move fast. Every change, from a new stat column to a full new page, is: edit the script, run python3 generate.py, get a fresh site in about a second, check it in a browser, ship it. There's no server to deploy, no migration to write, no cache to bust. The entire site is reproducible from two files any time.

03Copying the pros

Once the basics existed — player pages, team pages, standings, career leaders — the interesting work was figuring out which real stats sites' ideas actually translated to a backyard league, and which needed to be built from scratch because the data simply doesn't exist at this level (no exit velocity here, no pitch tracking, no Statcast).

A few things that did translate directly, modeled on Baseball Savant and Baseball-Reference:

Percentile rankings — the colored bar charts Savant uses to show where a player ranks league-wide in each stat, complete with an animated "Play" button that steps a player's percentiles year by year.

Park Factors — how much each field in the league inflates or suppresses offense, era-adjusted the same way OPS+ and ERA+ already are on the site, because this league's own scoring environment has swung by roughly 2.5x across its history. A flat, cross-era number would have just rewarded whichever field got used in a high-offense year.

Player Cards — a shareable PNG, rendered on a canvas, built from the exact same percentile and season-stat data already on the page, so the card can never say something different from the site itself.

04Games nobody asked for

At some point "stats site" turned into "stats site with an arcade," which nobody explicitly asked for but which turned out to be the most fun part of the project. There are three original games, all built entirely from the league's own real data:

Grid is an Immaculate-Grid clone: nine squares, each needing a player who fits both its row and column category (a franchise, an award, a career stat threshold). Getting this right took actual math — early versions could quietly become unsolvable if a player's guess order happened to use up the only name that fit some other square. The fix was a real bipartite-matching check at generation time, so every daily grid is now guaranteed to have a clean, no-repeat solution.

Stat Pad flips the format: instead of finding any right answer, you're finding the best one, submitting a player and a season to maximize a target stat under given constraints.

15-0 is a five-round fantasy draft — deal a real team-year, draft one player from it, repeat — followed by an actual 15-game simulation of your roster's season, bootstrapped from the league's own real distribution of final scores rather than a textbook bell curve. That simulation went through a real round of statistical debugging: an early version scaled run totals multiplicatively, which meant a great offense could still get shut out just as often as a bad one (zero times anything is zero), and it blew up rare high-scoring games into absurd ones. Switching to an additive shift, validated with a Monte Carlo test against the real historical run-total pool, cut blowout frequency roughly in half.

05Bugs worth telling

Some of the most interesting work on this site was diagnosing things that looked fine and weren't. A few favorites:

Field note — the invisible favicon

The site's icon showed up fine in a browser tab but never in Google search results. The cause: the favicon was a data: URI baked directly into the HTML. A browser that already has the page loaded can render that fine, but Google's icon crawler fetches the favicon from its own URL, independent of the page — and a data URI has no URL to fetch. Writing the icon out as a real favicon.png file fixed it.

Field note — three seasons of missing data

Park Factors was quietly excluding almost every game from 2017 through 2019 — not because the data was missing, but because the code required three or more individually-recorded batters per team to count a game as having "a box score." That threshold made sense somewhere else on the site, for attributing a stat line to one specific player. Park Factors never does that; it only sums a game's totals. The league's early games, which logged one combined team-total line instead of per-player lines, summed to the exact same real numbers a full box score would — the check was just measuring the wrong thing. Lowering the bar to one recorded batter fixed three years of "missing" history in one line.

Field note — real data beats a good guess

Every pitcher's win-loss record was blank for the current season — 52 games, all recorded as 0-0, even though the display code was already correct. I built an algorithm to infer the winning and losing pitcher from each game's inning-by-inning line score, and validated it against 426 historical games where the real answer was already known: 90.8% right. Good, but not good enough to publish as fact. It turned out the league's games are also tracked on a public wiffleball stats platform, which has an endpoint that returns the actual, official decision for any game. Real data beat a good guess, so that's what shipped.

Field note — the whole site was zoomed out

A layout bug on one page turned out to be missing a <meta name="viewport"> tag site-wide. Without it, phones render every page at a fake desktop-width canvas and zoom the whole thing out to fit the screen — which meant none of the site's existing mobile breakpoints had ever actually fired on a real phone. Adding one line fixed the original bug and, in the process, revealed a second one it had been hiding: every data table used a fixed width: 100%, which fights against text that isn't allowed to wrap, so tables started visibly overlapping themselves the moment real narrow-screen widths applied. A one-word change, from a fixed width to a minimum width, let tables grow to fit their content and scroll horizontally instead of colliding.

06The draft that's not done yet

Not everything on the build list has shipped, and that's deliberate. The most ambitious feature in progress is Game Score: a single number, inspired by hockey analytics, combining a player's hitting, pitching, and fielding into one per-game rating.

The formula went through several real rounds of revision before I'd trust it: hand-picked weights first, then validated against real outcomes for win-agreement, then found and fixed a bias where the same performance was worth up to 2.5x more or less depending on what year it happened in, then replaced several of the hand-picked weights with ones fitted by actual regression against the league's own team-game data. Along the way, a parallel effort scraped real play-by-play data from that same public wiffleball platform to build a genuine win-probability model — logistic regression, validated for internal consistency, cross-checked against every game.

None of it is live. The rule for this feature has been simple from the start: it doesn't ship until the formula is actually right, not just plausible. It's still sitting in a local draft, deliberately kept out of every other change that's gone out in the meantime.

07Fifteen years, written down

The newest page on the site isn't a stat page at all. It's the league's own origin story — the backyard pickup games, the six-team season in 2012, the field that got retired in 2022, the comeback title in 2025 — paired with photos going back to some genuinely blurry early-2010s front-yard action shots. Writing it wasn't a coding problem so much as an editing one: rewording a repeated turn of phrase here, reordering a photo rail there, adding names that deserved a mention. It's the one part of the site where the "build" was really just careful revision, a sentence at a time, until it sounded right.

08What this process is actually like

The honest version of "I built this with AI" is less like typing a wish into a box and more like directing an extremely fast, extremely literal collaborator who will confidently ship a bug if you don't check its work. The parts that made this project actually trustworthy weren't the parts where something got generated quickly — they were the parts where a claim got tested before it got shipped: running a Monte Carlo simulation against real historical data before trusting a formula change, validating an inferred stat against hundreds of games with known answers before deciding it wasn't good enough, screenshotting an actual phone-width browser before believing a layout was fixed.

Building software this way still means being the one who decides what's worth building, what's good enough to ship, and what needs another round before it's real. The tools got faster. That part didn't change.

If you want to see where all of this landed, the site is at bwbwiffleball.com — Players, Teams, Standings, Park Factors, an Arcade, and now fifteen years of history, in one place.
